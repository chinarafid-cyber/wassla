# بنية مشروع وصلة (Wassla) — Phase 1، وحدة AUTH-001

هذا الملف يشرح كيف بُني نظام المصادقة الحالي، وليش اخترنا كل أداة وقرار، بلغة مبسّطة.

## الفكرة العامة

وصلة منصة ويب تربط بين **أصحاب العلامات التجارية** و**صناع المحتوى (المؤثرين)** لإنشاء حملات إعلانية. المنصة تربح عن طريق عمولة نسبة مئوية من كل حملة (لم يُبنَ أي جزء متعلق بالدفع بعد).

## لماذا استبدلنا Supabase بنظام مبني من الصفر

النسخة الأولى (Phase 0) استخدمت Supabase (بريد إلكتروني + كلمة مرور). طلب AUTH-001 كان مختلفًا كليًا: **مصادقة برقم الهاتف عبر OTP، بدون كلمات مرور إطلاقًا**، مع تحكم كامل بالجلسات (JWT + إبطال فوري) وبنية تحتية ذاتية الاستضافة (PostgreSQL + Redis عبر Docker). هذا لا يتماشى مع نموذج Supabase الجاهز، فاستبدلناه بالكامل.

## الأدوات التقنية ولماذا

| الأداة | الاستخدام | لماذا |
|---|---|---|
| **Next.js 16** (App Router) | الواجهة + الـ API في مكان واحد | API-first فعليًا: كل شيء تحت `/api/v1/` يمكن لتطبيقات الموبايل استهلاكه لاحقًا بدون تغيير |
| **Prisma + PostgreSQL** | قاعدة البيانات | نموذج بيانات صريح ومُهاجَر (migrated)، أفضل من قاعدة بيانات بلا مخطط لنظام مصادقة |
| **Redis (ioredis)** | Rate limiting + cooldown | عدادات سريعة منتهية الصلاحية — Postgres غير مناسب لهذا النمط من القراءة/الكتابة المتكررة |
| **jose** (لا `jsonwebtoken`) | توقيع/تحقق JWT | موصى بها رسميًا في توثيق Next.js نفسه، تعمل بنفس الطريقة على Node وEdge |
| **bcryptjs** | تجزئة كود OTP | لا اعتماديات بناء C++ (مشكلة شائعة مع `bcrypt` على ويندوز) |
| **Docker Compose** | Postgres + Redis محليًا | بيئة تطوير مطابقة للإنتاج بدون تثبيت يدوي |
| **Vitest + Playwright** | اختبارات وحدة + شاملة | تغطية منطق العمل الحرج أمنيًا (OTP، JWT) بمحاكاة، والتدفق الكامل بمتصفح حقيقي |

## المصادقة: كيف تعمل فعليًا

```
زائر
  ↓ POST /api/v1/auth/otp/request  { phone }
  (rate limit بالهاتف + IP، cooldown 30 ثانية)
  ↓
كود مكوّن من 6 أرقام (crypto.randomInt، ليس Math.random)
يُحفظ مُجزَّأ (bcrypt) في جدول otps، صلاحيته 120 ثانية، أقصى 5 محاولات
  ↓ POST /api/v1/auth/otp/verify  { phone, code }
  ↓
تحقق ناجح → "تذكرة تحقق" (JWT قصير، 5 دقائق) — وليس جلسة كاملة بعد
  ↓
   إذا مستخدم جديد               إذا مستخدم موجود
   ↓                              ↓
   POST /register                POST /login
   (ينشئ المستخدم + جلسة)        (ينشئ جلسة فقط)
  ↓
Access Token (JWT، 15 دقيقة) + Refresh Token (نص عشوائي، 30 يوم)
كلاهما في كوكيز HttpOnly + Secure + SameSite=Lax
```

### قرار مهم: لماذا "تذكرة تحقق" منفصلة عن الجلسة؟

لو سجّلنا الجلسة فور نجاح OTP، أي زائر تحقق من رقمه لكنه لم يُكمل التسجيل كان سيُسجَّل دخول تلقائيًا بحساب غير مكتمل. التذكرة الوسيطة تفصل "أثبتنا ملكية الرقم" عن "أنشأنا/سجّلنا الجلسة"، ويطابق هذا تدفقك المطلوب حرفيًا: Verify OTP → (إذا جديد) Complete Profile → Login → Dashboard.

### Access Token مقابل Refresh Token

- **Access Token**: JWT موقّع، عديم الحالة (stateless) بالكامل، لا يلمس قاعدة البيانات عند كل طلب — يُتحقق منه بالتوقيع فقط. صلاحيته قصيرة عمدًا (15 دقيقة).
- **Refresh Token**: **ليس JWT** — نص عشوائي عالي الإنتروبيا (32 بايت)، يُخزَّن Hash منه (SHA-256، وليس bcrypt، لأنه عالي الإنتروبيا أصلاً ولا داعي لتجزئة بطيئة) في جدول `sessions`. هذا يعني الإبطال (تسجيل خروج) هو مجرد حذف/تحديث صف في القاعدة، فوري وموثوق، بعكس JWT الذي يبقى صالحًا حتى انتهاء صلاحيته حتى لو "أبطلناه".
- **تدوير (Rotation)**: كل مرة يُستخدم فيها الـ refresh token لتوليد access token جديد، يُستبدل بواحد جديد أيضًا. يقلّل هذا من الفائدة العملية لو سُرِق توكن قديم.

## `proxy.ts` بدل `middleware.ts`

Next.js 16 غيّر الاسم والاتفاقية: `middleware.ts` أصبح `proxy.ts` (دالة `export function proxy()`)، ويعمل حصريًا على Node.js runtime (وليس Edge) — هذا يسمح لنا باستخدام Prisma/Redis مباشرة داخله للتحديث الصامت للتوكن.

`src/proxy.ts` يقوم بـ:
1. **فحص متفائل فقط** (JWT signature، بلا استعلام قاعدة بيانات) لمعظم الطلبات — تطبيقًا لتحذير Next.js نفسه بعدم إثقال الـ proxy بفحوصات بطيئة.
2. **تحديث صامت**: فقط عندما يكون الـ access token منتهيًا/مفقودًا **و** يوجد refresh token صالح، يُنفَّذ استعلام قاعدة بيانات واحد لتدوير الجلسة.
3. إعادة توجيه غير المسجّلين بعيدًا عن الصفحات المحمية، والعكس (مسجّل يحاول زيارة `/login` يُعاد توجيهه لـ `/dashboard`).
4. صلاحيات الأدوار (`/admin`, `/merchant`) على مستوى الـ proxy، **بالإضافة** لتحقق مستقل في كل صفحة (`getCurrentUser()`) — لأن توثيق Next.js نفسه يحذّر من الاعتماد على الـ proxy كخط دفاع وحيد.

⚠️ **ملاحظة تصميمية اكتُشفت أثناء الاختبار**: كوكي الـ refresh token يجب أن يكون بمسار `/` (وليس `/api/v1/auth` كما كان مخططًا أول مرة) — وإلا فالمتصفح لن يرسله أصلاً لصفحات مثل `/dashboard`، ويصبح التحديث الصامت في `proxy.ts` مستحيلاً.

## طبقات الكود (Feature-Based Architecture)

```
src/features/auth/
├── schemas/       ← Zod: التحقق من المدخلات (هاتف، OTP، الملف الشخصي)
├── repositories/  ← الطبقة الوحيدة التي تتحدث مع Prisma مباشرة
├── services/      ← منطق العمل (otp.service, auth.service, session.service, dal)
├── components/    ← نماذج React الخاصة بالمصادقة
└── types/         ← DTOs (لا نُرجع صف Prisma الخام للعميل أبدًا)

src/lib/           ← بنية تحتية عامة: prisma, redis, jwt, cookies, csrf, rate-limit,
                     device, audit-log, hash, tokens, sms/, env
src/config/        ← ثوابت العمل (OTP_LENGTH=6, OTP_EXPIRY_SECONDS=120...) وخريطة الأدوار
```

الفصل بين `repositories` و`services` يسمح باختبار منطق العمل (`otp.service.test.ts`) بمحاكاة قاعدة البيانات بدل الحاجة لاتصال حقيقي.

## الأمان — كل بند من المتطلبات وكيف تحقق

| المتطلب | التنفيذ |
|---|---|
| Rate Limiting | Redis: حد للطلبات بالهاتف وبالـ IP، منفصل عن cooldown إعادة الإرسال |
| CSRF Protection | نمط Double-submit cookie يدوي (بعد استبعاد الحزمة الوحيدة المتاحة `edge-csrf` لكونها عالقة في RC منذ سنوات) |
| XSS Protection | React يُهرّب المخرجات تلقائيًا (لا `dangerouslySetInnerHTML` في المشروع) + رأس `Content-Security-Policy` |
| SQL Injection | Prisma فقط، بلا استعلامات SQL خام (`$queryRaw`) في أي مكان |
| Secure Cookies | HttpOnly + Secure (إنتاج) + SameSite=Lax على كل كوكيز الجلسة |
| Helmet Headers | مكافئها عبر `next.config.ts`: X-Frame-Options, X-Content-Type-Options, HSTS, Referrer-Policy, Permissions-Policy, CSP |
| Device Detection | `ua-parser-js` على كل جلسة (`sessions.deviceName`, `userAgent`) |
| IP Logging | على كل OTP وجلسة وسجل تدقيق |
| Audit Logs | جدول `audit_logs` مستقل، append-only، 12 نوع حدث، لا يحتوي أبدًا tokens أو أكواد OTP |

## ملاحظة بناء Docker: متغيرات بيئة وهمية في مرحلة البناء

`Dockerfile` (مرحلة `builder`) يحتوي على قيم `DATABASE_URL`/`REDIS_URL`/JWT secrets/Twilio **وهمية**. السبب: `next build` يستورد `@/lib/env` أثناء "تجميع بيانات الصفحات" ليقرر أي المسارات ديناميكية — وهذا يُشغّل تحقق Zod فورًا، رغم أن لا صفحة تُصنّع ثابتة فعليًا هنا (الكل ديناميكي، يحتاج جلسة حية). القيم الحقيقية تُحقن فقط عند التشغيل الفعلي للحاوية عبر `environment:` في `docker-compose.yml`. **لا اتصال حقيقي بقاعدة بيانات أو Redis يحدث بهذه القيم أثناء البناء.**

تحقق هذا فعليًا: بُنيت صورة `wassla-app` الإنتاجية كاملة وشُغِّلت بنجاح ضد Postgres/Redis حقيقيين (عبر `docker compose --profile full up`)، وتم تسجيل مستخدم واختباره كاملاً داخل الحاوية.

## قاعدة البيانات

4 جداول: `users`, `otps`, `sessions`, `audit_logs`. الأدوار (`VISITOR/CUSTOMER/MERCHANT/ADMIN`) مُنفَّذة كـ Prisma enum على `User.role` مباشرة بدل جدول علاقات منفصل — الأربعة أدوار ثابتة وحصرية (كل مستخدم له دور واحد)، فجدول Many-to-Many كان سيضيف تعقيدًا بلا فائدة حقيقية هنا.
